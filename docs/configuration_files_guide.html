OrderStepCondition

10reference/taxa_ref.csvtaxa_ref = TRUE
11Generated filesAfter user-entered reference files
12path/UAV_folder.csvAlways
13path/UAV_file_patterns.csvAlways
14path/vectors.csvMay be empty; ignored by the pipeline
15observatory.yaml and site HTML reportAfter the global configuration check

Operation 1 begins by creating only config/param, config/reference, and config/path. It creates no CSV. At each step, the table is editable immediately. An imported CSV or Excel file replaces the draft shown on screen but remains editable. The file is written only after Validate and save succeeds; Next file then opens the following applicable step.

Operation 2 loads an existing configuration. The published and candidate tables are shown side by side. Modified cells, deleted rows, and added rows have distinct colours. A panel below the tables lists the consequences for dependent configuration files and later data checks.

Every save checks the current file and its consistency with already validated files. Step 15 runs the complete configuration-only check. After it passes, the previous YAML and site check are moved to archive/, a dated modification report records before/after file contents, and all derived configuration reports are rebuilt. Same-day publications use _2, _3, and so on. Operation 1 never tests a configured path, opens scientific data, or requires server access. In operation 3, Shiny reads the server aliases declared in crownfile_param.csv and UAV_folder.csv and displays one local-root field for each alias. Operation 3 resolves the crownfile from those mappings and applies the publication lock before scientific-data checks. Every opened GeoPackage layer has its active sf geometry column normalized to geometry, including layers stored with a column named geom. The product scan always writes products_check.txt. A successful result displays PASS or PASS WITH WARNINGS and enables Generate or update all_products.csv plus a detailed or grouped raw/processed comparison. The four operations — Generate the config folder, Modify the config folder, Check parameters and data, and Visualise parameters and data — are available in Shiny and through direct R calls.

3. param/sensor.csv

  • Exact columns: sensor;survey;start_date;end_date;status.
  • Unique key: sensor/survey/start_date.
  • Dates use yyyymmdd; periods are inclusive. No overlap is allowed within a survey, including two periods of the same sensor. Gaps and end_date = start_date are allowed.
  • active requires an empty end_date and is open through today. not active requires an end_date on or after start_date.
  • A sensor may cover several surveys. A row for a FALSE survey or an active survey without any sensor is blocking. An active survey with historical sensors only produces a warning.
sensor;survey;start_date;end_date;status
Mavic2;RGB;20220730;;active

4. param/product.csv

The canonical catalogue contains 17 survey/product pairs. In the operation 1 Shiny editor, only rows belonging to surveys whose status is TRUE are displayed; the example below therefore corresponds to RGB only. On save, hidden rows for FALSE surveys are automatically retained with status FALSE so product.csv remains a complete canonical file. Every product of each active survey is present: at least one is TRUE, a FALSE product produces a warning, and a derived TRUE product with its raw product FALSE is blocking.

  • The crownfile is always a GeoPackage file with the .gpkg extension.
  • dynamic requires the geometry and infos layers and requires Tree_Status and Geom_Modif in geometry.
  • light contains exactly one spatial layer named crowns and does not require those two variables. Every crownfile_vars.csv row then has layer = crowns.

13. path/UAV_file_patterns.csv

ColumnMeaning and requirement
surveyCanonical protocol; forms an allowed pair with product.
productProduct declared in product.csv and, when a location exists, associated with the same pair in UAV_folder.csv.
directory_patternPattern applied to immediate child directory names. Fill this column or filename_pattern, never both.
filename_patternPattern applied to immediate child file names. Fill this column or directory_pattern, never both.

This file defines how products are discovered below each configured location. The operation 3 scan is non-recursive: a directory_pattern identifies an immediate child directory as a product object; a filename_pattern identifies an immediate child file. A pattern acts on the immediate name only and cannot contain / or \. A survey/product pair occurs at most once. An active pair or a pair configured in UAV_folder.csv without a pattern produces a warning; a retained pattern for a FALSE product also produces a warning.

Every RGB, MS, or DLS pattern contains exactly one supported date placeholder. tree_pictures is exempt. Braces are balanced, names are case-sensitive, and a captured field can occur only once.

Explicit crown-value transformation

{crownfile.infos.tax_sp_level|space_to_hyphen}

The |space_to_hyphen suffix declares that spaces were represented by hyphens in the object name. The convention turns Lophira alata into Lophira-alata; discovery restores spaces in the captured value. Review scientific names containing meaningful hyphens manually.

Discovery result

Every captured placeholder becomes a column in all_products.csv. The standard columns are always survey, product, server, configured_path, relative_path, object_name, and object_type. Absolute local server roots are never exported. The exemple column of crownfile_vars.csv documents representative crown values; discovery reads object names and never modifies scientific files.

A. Inventory files

FilePurpose
all_products.csvInventory written or updated on request after a successful connected check, including a check with warnings only.
products_check.txtDiagnostics written automatically for every product-inventory scan and refreshed with all_products.csv.

compare_raw_processed() returns one row per survey, date, and processed product. With group_by_processed_status = TRUE, it sums raw_count and processed_count for each processed_product/status pair. Status values are completed, missing_processed, and processed_without_raw. Shiny offers this comparison after a successful check; interactive tables have one filter per column.

B. Required consistency between files

SourceRequired consistency
survey → sensorEvery active survey has a sensor; FALSE surveys have no sensor row.
survey → productEvery catalog row exists; inactive surveys have only FALSE products; every active survey has a TRUE product.
product → UAVMissing folder or pattern for an active product: warning; retained inactive mapping: warning.
survey → zoomstree_pictures controls the zoom file; every tree_pictures sensor has at least one zoom.
crownfile_param → crownfileserver and path locate the file; crownfile_type, plots_list, taxa_ref, and dawkins determine its mandatory schema.
configuration → YAML/HTMLEvery change requires publication again; no scientific data are modified.
dynamic → datesWhen RGB and RGB_orthomosaic are active, crown dates are compared with observed orthomosaics; absence: warning.

C. Configuration evolution

Shiny compares the published and candidate versions simultaneously; modified cells, deleted rows, and added rows are coloured. config_change_impacts() describes dependent files to create, fill, or check. In direct R use, operation2_modify_config(), preview_config_table_change(), and generate_config_outputs(before_snapshot = ...) provide the same information. After successful global validation, publication archives the previous observatory.yaml and site_check.txt, moves the active modification report into archive/ without renaming it, rebuilds outputs, and writes modification_yyyymmdd[_n].txt. Before/after CSV blocks remain raw. YAML blocks are also raw and grouped at the end; the derived HTML report is excluded from the log. The _2, _3, and later suffixes prevent same-day collisions. Scientific data are never modified.

D. Reserved functions

  • The columns and semantics of vectors.csv are not defined; its contents are ignored.
  • taxa_ref.csv has no content model and taxa_id values are not compared in 3.1.0.
  • Dawkins parameters are stored and checked, but the class-assignment algorithm is not run.

L’opération 1 commence par créer uniquement config/param, config/reference et config/path. Aucun CSV n’est créé à ce stade. À chaque étape, le tableau est immédiatement modifiable. L’import d’un CSV ou d’un fichier Excel remplace le brouillon affiché, qui reste modifiable. Le fichier est écrit uniquement après la réussite de Validate and save ; le bouton Next file ouvre alors l’étape applicable suivante.

L’opération 2 charge une configuration existante. Le tableau publié et le tableau candidat sont affichés côte à côte. Les cellules modifiées, les lignes supprimées et les lignes ajoutées ont des couleurs distinctes. Une fenêtre sous les tableaux décrit les conséquences pour les autres fichiers de configuration et les futurs contrôles de données.

Chaque sauvegarde contrôle le fichier courant et sa cohérence avec les fichiers déjà validés. L’étape 15 exécute le contrôle global limité à la configuration. Après sa réussite, le YAML et le contrôle de site précédents sont déplacés dans archive/, un rapport daté conserve les contenus avant/après, puis tous les rapports dérivés sont reconstruits. Plusieurs publications le même jour utilisent les suffixes _2, _3, etc. L’opération 1 ne teste aucun chemin configuré, n’ouvre aucune donnée scientifique et ne nécessite aucun serveur. Dans l’opération 3, Shiny lit les alias déclarés dans crownfile_param.csv et UAV_folder.csv et affiche un champ de racine locale pour chacun. L’opération 3 résout le crownfile depuis ces correspondances et applique le verrou de publication avant les contrôles de données scientifiques. La colonne géométrique sf de chaque couche GeoPackage ouverte est immédiatement renommée geometry, y compris lorsqu’elle est stockée sous le nom geom. Le scan des produits écrit toujours products_check.txt. Un contrôle réussi affiche PASS ou PASS WITH WARNINGS et active Generate or update all_products.csv, ainsi qu’une comparaison raw/processed détaillée ou regroupée. Les quatre opérations — Generate the config folder, Modify the config folder, Check parameters and data et Visualise parameters and data — sont disponibles dans Shiny et par appels R directs.

Transformation explicite d’une valeur crown

{crownfile.infos.tax_sp_level|space_to_hyphen}

Le suffixe |space_to_hyphen indique que les espaces ont été remplacés par des tirets dans le nom de l’objet. La convention transforme par exemple Lophira alata en Lophira-alata ; la découverte restitue les espaces dans la valeur capturée. Vérifier manuellement les noms scientifiques contenant des tirets significatifs.

Résultat de la découverte

Chaque placeholder capturé devient une colonne de all_products.csv. Les colonnes standard sont toujours survey, product, server, configured_path, relative_path, object_name et object_type. Les racines absolues locales des serveurs ne sont jamais exportées. La colonne exemple de crownfile_vars.csv documente des valeurs crown représentatives ; la découverte lit les noms d’objets et ne modifie aucun fichier scientifique.

C. Évolution d’une configuration

Shiny compare simultanément la version publiée et la version candidate ; les cellules modifiées, lignes supprimées et lignes ajoutées sont colorées. config_change_impacts() décrit les fichiers dépendants à créer, remplir ou vérifier. En R direct, operation2_modify_config(), preview_config_table_change() et generate_config_outputs(before_snapshot = ...) fournissent les mêmes informations. Après une validation globale réussie, la publication archive les anciens observatory.yaml et site_check.txt, déplace le rapport de modification actif dans archive/ sans le renommer, reconstruit les sorties et écrit modification_yyyymmdd[_n].txt. Les blocs CSV avant/après restent bruts. Les blocs YAML, également bruts, sont regroupés à la fin ; le rapport HTML dérivé est exclu du journal. Les suffixes _2, _3, etc. empêchent toute collision le même jour. Aucune donnée scientifique n’est modifiée.

D. Fonctionnalités réservées

  • Les colonnes et la sémantique de vectors.csv ne sont pas définies ; son contenu est ignoré.
  • taxa_ref.csv n’a pas de modèle de contenu et les valeurs taxa_id ne sont pas comparées dans la 3.1.0.
  • Les paramètres Dawkins sont stockés et contrôlés, mais l’algorithme d’attribution des classes n’est pas exécuté.
